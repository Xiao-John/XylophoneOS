# XOS 开发纪律：认真做系统，轻松一起玩

XOS 是自己和朋友的 OSdev 项目。路线以 `xos_plan.md` 正文为准，目标是
x86-64、NASM + 受限 C++、微内核和最终可用的 GCC/G++ 开发环境。
本文件约束开发与交接，不额外制造审批阶段。

## 开始一组任务

先读 `state.md`、计划与相关工作记录，确认已完成什么、哪些只是建议、哪些
尚未验证。声明本组范围和预期证据；能根据已确认路线作出的局部可逆选择，
直接推进并记录。用户说“先不写”时只讨论，不擅自实施。

多个 agent 工作时，在 `state.md` 的“正在进行”中登记任务、负责者和文件范围。
避免同时修改同一文件；交接时说明未完成修改，不把其他人的改动覆盖或清掉。
没有可靠并发协调机制时，由主 agent 汇总共享状态文件。
当前 `build/` 也是共享目录，不并发构建或清理；汇总修改后由一位 agent
执行最终构建和验证，避免把不同代码版本的产物与日志混在一起。

## 文件结构

- `src/boot/x86/`：16 位启动与架构过渡代码。
- `src/kernel/`：后续内核；需要时创建，不先堆空目录。
- `src/user/`：用户态服务、装载器与程序。
- `src/shared/`：内核/SDK 共用的实际 ABI 与最小运行时，不暴露内核内部结构。
- `scripts/`：宿主构建、运行、验证工具，不代替 XOS 运行时服务。
- `tests/`：验证真实行为的测试与故障输入。
- `docs/`：计划、当前状态、决策、设计和开发记录。
- `build/`：可重建产物、清单和验证日志；不存唯一源码。
- `localpilot/`：独立相关项目，保持隔离；不进入 XOS 的构建、扫描或清理。

自研标识符与新文件默认 snake_case；`Discipline.md` 按用户指定保留。
上游代码、标准 ABI 和外部工具要求的名字遵循原约定。
新增目录按实际职责建立，不把架构、驱动、业务和测试混成单个文件。

## 固件、指令集和通用内核的边界

固件接口只放在对应引导器内；通用内核不调用 BIOS/UEFI，不包含固件原始结构。
引导器把内存信息整理为 `xos::boot_info` / `memory_region`，架构入口负责调用约定。
寄存器、页表格式、异常入口、CPU 汇编放在 `src/kernel/arch/<isa>/`；
设备端口和板级地址放在 `src/kernel/platform/<platform>/`。
`core/` 只依赖通用头文件与实际实现的平台接口，不出现内联汇编和硬件地址。
构建只选择一种已实现的后端，不把所有架构目录递归编译进同一个目标。

不为可移植性提前实现第二套 OS 后端。当前用第二种 ISA 编译通用代码，及时
发现耦合；编译通过只记为编译检查，不冒称跨架构启动。详见 `architecture_and_boot.md`。
ELF 解析与装载策略放用户态，内核只提供带所有者和生命周期检查的机制。
新增用户 ABI 时同步共享头、SDK、真实客体测试和 `e04_loader_sdk.md`。

## 一组任务完成后的交接

每组完成时必须更新 `state.md`，并新增一份 `work_log/NNNN_主题.md`，至少写清：

1. 任务范围、已完成行为和修改文件。
2. 本组选择与原因；影响后续的决定同步到 `decisions.md`。
3. 实际执行的构建/运行命令、工具版本、配置、产物标识与证据位置。
4. 通过、失败、未运行的检查；已知限制和未完成内容。
5. 下一位 agent 可直接执行的下一步，以及不能误认成已实现的功能。

`state.md` 是当前摘要，工作记录保留过程和证据，计划保留目标；不要求下一位
agent 从聊天记录猜状态。实现改变时同步相关说明，失败也要落盘。
测试日志可放 `build/`，但关键结论、哈希和失败原因也写入持久文档，避免
清理产物后交接失忆。没有执行的检查标为“未运行”，不以跳过冒充通过。

## 工程尺度

先让本组真实跑通，再扩大范围。独立启动、用户隔离、原生编译、系统重建、
编译器自举分别报告。欢迎串口文字不等于微内核完成。
真实错误返回真实失败，不写永远成功的占位接口。保留有用调试信息与符号。
只写专用测试镜像，不操作宿主真实分区，不破坏用户源码或另一个项目。

## 轻松愉快准则

允许无害彩蛋、里程碑外号和朋友间的玩笑。彩蛋小而可关，不能吞掉错误、
增加随机故障、制造延迟、篡改文件或改变权限语义。诊断先把事情说清楚，
笑话随后再讲。不能为一个梗提前建设一整个子系统。

把阶段成果做成能看、能操作的小演示；朋友把程序玩崩也是有价值的反馈。
不以优于 Linux、发论文或商业化为快乐的前提。遇到 bug 如实记录，一起修，
不把开发记录变成检讨书。下划线已经获胜，不必再发动命名战争。
