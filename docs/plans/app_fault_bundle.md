# 应用故障包计划：从退出状态到可定位的离线报告

2026-10-29，基线 `94f8e30`。用户已要求编写计划；本文是待实施方案，
FB0–FB4 均未实施、未运行专项验收，不分配新 ABI，不改既有资格。

## 目标与首版范围

朋友运行应用后，若发生异常，启动者能留下一个有界、可导出、能与正确源码和
符号文件对应的报告包。即使保存报告失败，原始应用结果仍清楚可见。

首版服务由受控启动者创建的普通用户程序：先接 xsh 的一个显式诊断运行入口，
再根据实际需要接其他启动者。复用现有父子进程等待，不承诺全系统自动收集。
首个演示为故意非法访问的程序退出后生成报告，宿主解析出对应源码位置；另一个
正常程序仍可运行。宿主符号化与 XOS 内生成报告分别验收。

不在首版实施：内核 panic/断电报告、完整 core dump、任意进程内存读取、所有线程
快照、自动上传、自动重启、全局日志服务或 GUI 崩溃对话框。OOM、显式 kill、
普通非零退出与 CPU 异常分开分类；分配失败不一定意味着程序退出。

## 已有能力与实际缺口

| 当前源码 | 已有行为 | 对计划的含义 |
|---|---|---|
| `src/shared/include/xos/process_abi.hpp` | 48 字节 `process_status` 含 version、outcome、pid、code、vector、address、instruction | 足够做基础异常报告；不含通用寄存器、故障 TID、异常 error code 或栈字节 |
| `src/kernel/arch/x86_64/tasks.cpp` 的 `user_fault` / `finish_task` | ring3 异常记录向量、CR2（仅 page fault）和 RIP；结束整个进程并保留父进程完成记录 | 首版在正常故障回收之后使用保存的状态，不延缓地址空间回收 |
| 同文件 `sys_process_wait` / `deliver_wait` | 按真实父 PID 查完成记录；成功复制后消费记录；当前完成记录表为 16 项 | 收集必须接在已有 wait 的单一消费者上，不能另起进程再次 wait |
| `src/user/programs/supervisor.cpp` 的 `result_line` | 读取 wait 结果并输出摘要 | 可在读到结果后调用用户态报告代码，保持原退出语义 |
| `src/user/loader/load.cpp` | 用户态打开并持有待装载文件版本进行验证与装载 | 需要新增同一打开实例的摘要/装载回执，不能故障后按路径重开来猜原程序 |
| 文件服务、构建 manifest、宿主 Binutils/LLDB | 已有文件 I/O、持久化和符号工具 | 尚无统一故障包格式、匹配校验、配额与导出使用流程 |

串口内核日志里有 TID，不代表父进程 ABI 返回 TID。首版不解析全局串口输出来
反推授权故障信息，也不把内核内部 `interrupt_frame` 当公共结构传给用户态。

## 分层与数据流

1. 启动者在装载阶段形成运行回执，关联程序实际字节摘要、SDK/profile、装载布局、
   系统 build ID 与本次运行 ID。实际 ELF 摘要必须对应装载使用的同一文件实例；
   映像内置模块则关联构建清单。缺失信息保留 unknown，不按文件名认定版本。
2. 内核按既有隔离、异常和回收机制返回 `process_status`。首版不新增 syscall。
3. 原 wait 消费者先取得状态，再交给用户态编码器生成报告。报告代码不得改变
   应用 outcome/code，也不得再消费同一完成记录或阻塞进程资源回收。
4. 用户态保存器通过已有文件服务写入私有报告目录；文件服务不理解报告内容。
   归档、压缩、脱敏、导出和保留策略均在用户态或显式宿主工具中完成。
5. 宿主工具验证包和符号匹配，使用交叉 `addr2line` 或 LLDB 解析故障指令地址。
   没有已验证的栈帧输入时只报告故障位置，不伪造调用栈。

首版建议将编码与保存拆成可复用用户态模块，先由启动者调用；是否独立为常驻
收集服务留到真实并发消费者出现后评估。不因为报告目录叫 crash 就授予全局观察权。

## 报告格式与来源标记

拟定目录为显式选择的 `<report_root>/<run_id>/`，不是已存在的系统路径。
`run_id` 由收集器生成、仅使用固定字符集合，并独立于 PID；PID 只在其运行会话
范围内解释。运行 ID 不授予任何进程或文件访问权。

| 文件 | 首版内容 | 来源/边界 |
|---|---|---|
| `report.json` | format_version、生成阶段、run_id、outcome/code、原始状态版本、PID、vector/address/instruction及各字段有效性 | fault 数据来自 wait；非 page fault 的零 address 不解释成“访问零地址” |
| `image.json` | 实际 ELF SHA-256、字节数、装载段/偏移、SDK/profile和可用构建标识 | 用户态装载回执；包版本/应用自报名称单独标记，不是内核认证事实 |
| `context.json` | 收集器版本、系统标识来源、单调时间及可用墙钟、日志截断/保存失败摘要 | 缺失时钟不伪造时间；不预设已有可查询的内核 boot UUID |
| `log.txt`，可选 | 显式启用的当前应用日志片段 | 默认为无；不从其他应用或全局控制台“顺便”收集 |
| `manifest.json` | 各内容文件的相对路径、字节数、SHA-256、格式版本与完整/部分标记 | 不循环包含自身摘要；整包目录不等于加密或签名 |

拟采用 UTF-8 JSON，地址/64 位标识用固定规则的十六进制字符串，避免经过其他语言
工具时丢失精度。明确字段必需性、最大长度和未知版本拒绝规则；错误文本须转义。
宿主解析器拒绝重复键、路径逃逸、重复文件名、超深结构、摘要不符和超预算输入。
SHA-256 检查完整性和输入关联，不证明来源可信，也不替代共享前的内容检查。

通用寄存器、error code、栈与 TID 均标为首版 unavailable，不填零冒充真实快照。
宿主原始串口/QEMU 日志只能作为单独的人工附加材料，不能默认并入应用授权日志。

## 单一 wait、线程与权限

- FB0 先覆盖 xsh 直接启动并等待的一个子进程。dash 的孙进程异常由其真实父进程
  观察；没有接入前明确 unsupported，不把整个进程树宣称已覆盖。
- 不改变 `process_status` 大小/版本，不向保留字段塞数据。保留既有 wait 只消费一次、
  错误输出缓冲不消费结果、并发 waiter 拒绝等语义，并做回归。
- 当前工作线程异常结束整个进程。首版能记录进程 fault，却不能从 wait 判断是哪条
  线程；线程归因属于 FB3，不能以串口日志现象替代接口证明。
- 默认不收集 argv、环境、文件内容或内存；用户明确选择附加内容时逐项登记大小、
  来源与暴露范围。文件路径和原始地址也可能敏感，导出前提供清单预览。
- 读取子进程结果沿已有真实父子关系，不为名叫 collector 的程序开放查询任意 PID。
  收集器死亡时沿现有父子回收规则处理，首版不承诺独立存活或报告必达。
- exec、fork、PID 复用、重启的身份边界先在 FB0 核对。首版不能关联的 exec 链明确
  标记来源未知，不用原始路径摘要冒充替换后的 ELF 摘要。

## 有界资源、持久化与降级

以下是候选预算，FB0 通过探针后冻结；不是当前实现限额：

| 项目 | 候选上限 |
|---|---:|
| 每包文件数 / 总量 | 8 个 / 128 KiB |
| 元数据总量 / 可选日志 | 32 KiB / 64 KiB |
| 自动保留数量 / 总量 | 16 包 / 2 MiB，两者同时约束 |
| 日志捕获并发 | 首版 1 个受控运行；额外运行真实拒绝 |

日志捕获默认关闭；后续 opt-in 捕获必须复用真实 FD/pipe，边读边做有界缓冲。
不能先等子进程退出再读满管道，不能让两名消费者竞争同一个输出流，也不能悄悄
改变终端交互。管道排空与等待协调若当前底座不足，先报告缺口，不能忙轮询补假实现。

创建独立目录、以临时名称写内容，逐项检查短写、close 与 sync，最后发布完整 manifest。
具体发布方式在 FB0 核对文件服务创建/rename/错误语义后冻结；不能直接借用 xypm 或
编辑器的事务承诺。中断留下的目录没有完整标记即为 partial，宿主不得按完整包接受。

未获得可靠持久化结果时报告保存失败或 UNKNOWN，不显示“已保存”；输出最小的
串口故障摘要作为退路。原应用结果始终保留，报告失败不递归生成另一份故障包。
在满盘、只读、文件服务退出或 I/O 故障下核定等待能否返回；若现有 IPC 会无限阻塞，
须把自动保存标为 blocked，先补可复用失败/等待机制，不能承诺未验证的超时。

配额用收集器自己的索引和内容核对，不删除用户指定目录中的未知文件。首版满额时
拒绝新增并提示显式清理；自动淘汰属于后续策略。正常 sync/重启恢复与任意断电安全
分开，首版只验前者。磁盘报错后仍应保留串口救援，不承诺故障文件服务自动恢复。

## 符号关联与可选快照

FB2 以运行 ELF 摘要关联同次构建保留的带符号 ELF、源码提交和 manifest；运行映像
剥离调试信息时，须在构建时建立两者的可核对映射，不能要求两份文件哈希相同。
ET_EXEC 使用实际装载地址；未来可重定位映像先增加 load bias 契约，再支持解析。
只有模块名相同、符号摘要不匹配、符号缺失或地址不在可执行段时输出明确未解析状态。

FB3 再评估 TID、通用寄存器、error code 与有界用户栈快照。新增机制前说明：为什么
现有 wait 不足、哪个主体可读、在何时复制、如何与线程退出/exec/回收竞争、最大保留量
及读取后消费/丢弃规则。复制须在地址空间仍有效时完成，只读合法用户映射，不做 fault
路径动态分配、不遍历不可信帧链、不等待文件服务，不泄露内核地址或其他进程内存。

若确需新 ABI，另做版本/尺寸/ISA 标记与授权对象设计，按
[ABI 登记](../contracts/abi_registry.md)先登记再实施；本文不预占 80–95 或其他编号。
不能把宿主 LLDB 全寄存器读取包装为客体已有故障查询接口。

## 分期、交付与验收

| 阶段 | 交付 | 必须证明 |
|---|---|---|
| FB0 勘查与格式冻结 | wait/装载/文件链路清单、格式/预算、权限与身份模型、可重复故障夹具 | 同一装载实例的摘要可取得；wait 消费位置唯一；满盘/服务失败的真实返回行为；尚无快照 ABI |
| FB1 客体最小报告 | 显式诊断运行、状态编码、配额与失败退路 | 除零/#UD/page fault 分类与 RIP；普通退出/kill不伪装成 CPU 异常；无文件权限、满盘、部分写和重复运行；应用资源回收 |
| FB2 离线定位闭环 | 报告导出、符号索引和宿主解析器、使用说明 | 正确源码行；错误/缺失符号拒绝；文件替换后仍关联原 ELF；sync/重启逐文件字节与摘要一致；坏包与预算边界 |
| FB3 可选诊断增强 | 独立设计后的 TID/寄存器/栈与 opt-in 日志 | 未授权读取拒绝；并发故障/exec/退出/收集器死亡与身份复用；超额无泄露；不可展开时保留原始状态 |
| FB4 用户交付 | SDK/profile、工具 XPK、朋友复现流程 | 干净安装、升级/卸载只处理归属文件；实际失败程序→导出→维护者定位；用户报告不被卸载自动删除 |

FB1/2 可不等 FB3。每个阶段独立记录 pass/partial/fail/not_run；暂不承诺完整 core 格式
或 GDB 原生 core 兼容。每组真实 guest 夹具还要证明故障后第二个正常程序可运行，
线程/页/完成记录/文件句柄回到声明基线；报告文件占用与泄漏计数分开。

证据绑定源码、工具链、系统/SDK/profile、运行及符号 ELF 摘要、QEMU 命令、原始输出、
报告内容与宿主解析命令。宿主解析通过不代替客体报告生成；旧异常测试不代替新保存测试。

## 文件范围与接续

实现时按实际职责拆分用户态编码/保存模块、启动者集成、`scripts/` 离线解析工具和
`tests/` 故障/错误输入；先在独立 `codex/` 分支登记具体路径和私有构建目录。
FB0–FB2 原则上不改内核，若探针证明需要公共缺口，另登记其最小范围与理由。
FB3 内核/共享头/SDK的改动单独评审，避免把 JSON、ELF 符号或报告路径放入内核。

下一步是 FB0：先用现有 `fault` 和线程故障探针复核真实状态，冻结单一 wait 接入点，
再写格式和保存失败夹具。来源/许可证按[许可纪律](../licensing.md)登记；首版优先复用
现有工具，不为报告包另引入压缩库。当前仅有本文，无实现产物或新验收结果。
