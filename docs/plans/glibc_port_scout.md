# glibc 移植工作面与加固期时机勘查

2026-11-12。状态：勘查；glibc 为用户选择的长期方向，尚未锁源、交叉构建或客体验证。本文不改变 XOS 宪法、现有 SDK 的默认实现或历史资格。勘查基线为本地 HEAD `45c2239e2b877f32f7d63f7241bb5f9f854fb22f`；主工作区同时存在其他未提交工作，本勘查未将其作为 glibc 的交付输入。未访问或同步远端仓库。

## 时机裁决

现在启动隔离的 glibc 移植纵切片，而不是等上层端口继续积累。加固期的目的包含降低将来的改动面：尽早发现运行时、线程、ABI 和工具链的结构冲突，避免新程序无意识依赖 newlib 私有细节。现有 newlib 系统和加固回归继续作为对照；候选 libc 在独立输出目录和独立 SDK 中建设，不覆盖公共 `build/`、已有应用或工作区改动。

启动移植不等于立即切换默认 libc，也不需要等待所有 POSIX、网络或完整浏览器。切换默认 SDK、发行及重建现有应用属于后续明确验收门；每个可见阶段必须明确通过、失败、未运行和受限范围。

| 虚拟内存 | [VM 路线](virtual_memory_cow.md) 记录 VM0–VM3 已实现、VM3 SDK 为 `implemented_unqualified`，COW1 为隔离探针受限通过，完整生命周期和 COW2/3 未验。当前 `newlib_syscalls.cpp` 仅接受受限匿名私有映射并要求初始 `PROT_NONE`；glibc 是否能使用该 profile 是待测问题，不能从旧 POSIX 快照里的 ENOSYS 推断现状，也不能把定向通过等同完整 mmap。 |

## glibc 的实际工作面

1. **来源与构建闭包。** 选定具体稳定版本并核对发布源、提交/归档哈希、补丁、构建工具和许可证；锁源前不宣称选定版本已验证。检查 glibc 的 `sysdeps`、目标识别、构建生成器、交叉工具链与 host 工具要求；禁止把 Linux 目标构建成功冒充 XOS 端口。glibc 上游说明 OS/架构相关实现由 `sysdeps` 选择；GNU Hurd 使用自己的 IPC 系统接口，是可研究的参考而非 XOS 可直接复用的后端。参见 [glibc 移植手册](https://snapshots.sourceware.org/glibc/trunk/2026-03-20_13-09_1774012141/manual/html_node/Porting.html) 和 [Hurd glibc](https://www.gnu.org/software/hurd/glibc.html)。
2. **启动与 ABI。** 定义 XOS 独立目标身份、ELF 入口、栈、argc/argv/env、辅助向量、构造/析构、静态 TLS、`errno`、退出和故障边界；审计 glibc 内部 ABI 与 XOS 进程/用户地址空间约束。动态装载器、`PT_INTERP`、动态 TLS 和符号版本属于后续明确工作项；先静态验证不构成永久排除。
3. **线程与同步。** 分清 glibc 自身线程实现与 XOS 通用线程/等待机制的职责，映射线程创建、栈和 TLS、锁与等待、信号、取消、join、退出回收；对现有单线程和线程 SDK 分别制定迁移关系。Linux futex、线程描述符或 syscall 数字不能假设天然适用。
4. **内存与装载。** 比对分配器实际映射、保护、回收、对齐和失败需求与 sys67 语义；缺口逐项举证。COW、共享/文件映射和动态链接各自验收，不能为编译便利绕开权限或回滚要求。ELF 解析仍归用户态。
5. **服务与 POSIX。** 通过 XOS SDK 和现有用户态服务接入文件、FD、进程和终端；网络/DNS/证书待相应用户服务具备实质行为。新内核机制按 C20 论证，身份、生命周期和失败语义遵循 C22/C25；不在内核实现 libc 业务或引入未经裁决的 Linux ABI。
6. **工具链、包与回归。** 目标 sysroot 中 crt、libc、libm、libgcc、libstdc++、头文件、包 profile 和 manifest 一起绑定；检测宿主头/库污染、交叉链接、静态重建和 XOS 目标身份。保留 newlib profile 作为对照，避免新旧 libc/线程对象在单个进程混用。
7. **发行与许可。** 逐文件确认锁定版本 glibc 和其他依赖的许可证、例外、修改与源码来源；针对静态程序准备可供替换/重链接的实际交付方案，并在发行验收前复核，不能把普通材料扫描等同完整法律结论。

## 本周期可执行的纵切片

按依赖执行，每个子项都给出版本、源码与工具哈希、构建命令、失败日志和下一项，不以占位函数报告成功：

1. **G0 基线与源调查。** 建独立目录；冻结本地代码及 SDK 对照标识，选定 glibc 候选源码并核来源和许可；从实际配置提取目标识别、`sysdeps`、启动、TLS、线程/内存及链接的第一批真实依赖。形成调用/语义/提供方/现状/证据/阻塞/负责人矩阵。网络或源不可用时记 NOT_RUN，不伪造哈希。
2. **G1 交叉构建探针。** 建立 XOS 专属、与 newlib 分开的 sysroot 和最小构建探针；验证配置实际选择的后端、目标对象、符号、头文件和构建来源，记录首个真实阻塞。宿主交叉编译通过只表示构建，不等于客体可运行。
3. **G2 静态单进程纵切片。** 从真实 XOS 客体启动候选 glibc 程序，验证入口、退出、`errno`、malloc/free、stdio 及基本错误；捕获串口、资源回收、ELF/库/SDK/镜像哈希，并以现有 SDK 同场景作对照。所需接口必须是正确实现或真实失败，不引入假成功。
4. **G3 线程与文件纵切片。** 通过锁与并发、TLS/errno 隔离、线程退出和资源回收，以及文件/FD 错误、服务死亡与继承的客体用例；按实测依赖增补通用机制。不要将单线程 `hello` 升格为线程或 POSIX 资格。
5. **G4 双 profile 与应用迁移。** 固定候选 SDK 和包 profile，对 shell、日常工具、C++、Qt/Python 等按各自已通过的基线逐项重建及客体对照；不能混合新旧 libc，也不将未重建应用声明已迁移。浏览器和联网在相应依赖成熟后另行验证。

G0–G3 从现在启动，作为加固周期中的基础能力线；和缺陷修复按文件/ABI 范围协调，避免共用构建产物和重叠写入。已有存量修复、发行及用户工作不自动等待 glibc；新端口优先隔离 libc 私有假设并登记真实缺口，避免无谓继续扩大依赖。

## 从加固期走向默认切换的门

- glibc 版本和来源、许可证与重链接方案、sysdeps 和升级维护责任已核实；能从锁定输入重建候选工具链和 SDK。
- G2/G3 及其负向、故障/取消和资源回收在真实客体通过，VM/线程/文件与构建产物资格均绑定当前代码，不以旧报告改绑。
- 已定义双 profile 的包/ELF/升级与回退策略，代表性现有应用完成逐项重建和行为回归；未迁移应用与不兼容项列明。
- 当前加固线上与运行库、文件、进程和装载器共享的改动已合并并针对最终组合重新验证；不以冻结日期或主机编译替代实际 gate。
- 动态链接、网络、完整 POSIX 和 WebKit 分别有明确未完成项与出口；它们不由新 libc 的名称自动取得资格。

正式切换是否满足上述门由实际证据决定，不预填日期或通过率。此勘查只做本地文档与源码核对；未获取 glibc 源码、未构建新 libc、未运行新测试，也未操作远端。
