# Issue 37：路径扫描与证据哈希核对

状态：**PARTIAL**。本次新增提交前扫描和证据索引校验，不能声称主仓库历史证据
中的个人路径已经清理，也不关闭 Issue 37。

## 范围和设计

- 路径扫描器检查 Git 暂存区、指定提交或工作树的实际内容，包括 gzip、tar、zip、
  归档成员名和链接、JSON 转义及部分二进制文本。无法解析或超过限制的内容标记为
  `UNVERIFIED`。匹配结果不复制个人路径文本。扫描能力有边界，不等同于隐私审计全覆盖。
- `scripts/ssg_public_paths.py` 为已知路径根提供模板，并允许严格拒绝未知私人路径；
  模板必须与实际执行命令和环境配置分开记录。
- `scripts/verify_evidence_index.py` 对当前工作树或某个 Git 提交中的索引和文件逐项
  核对 SHA-256，并支持同时记录文件字节数的索引；空索引、缺失文件、错误摘要、
  错误长度和不安全路径不得报通过。它验证文件
  一致性，不重新执行客体测试，也不证明历史验收结论。
- PR 工作流对合并结果相对于基础提交的实际文件内容进行扫描。基础分支已有扫描器时
  使用基础分支版本，避免 PR 自行移除其检查。这个门槛不清理已有历史或远端副本。
- 两份尚在 `work_log/` 的历史命令改为明确标注的可配置模板；原始命令仍在 Git 历史。
- 两组已入主线的冻结证据中，10 份混合换行串口日志曾被 Git 换行归一化，致使
  原索引不匹配。从保留的原工作区取回与原索引逐项一致的原始字节；索引未修改。
  `.gitattributes` 对冻结报告禁用文本转换，以保护索引覆盖的 JSON、日志等文件；
  [恢复清单](0149_issue37_serial_recovery.json)
  分别记录基础提交的归一化字节和恢复字节的 SHA-256。

## 基线与验证

基础提交 `0a91a2bb1eabd6977f1001ac8bd7781a88fae225`：文档中直接文本搜索某个
已知本机主目录得到 339 个文件；全量文档扫描还在压缩内容及其他主目录中识别到更多
待审位置。两组数字覆盖范围不同，不能当作新 PR 引入的全部泄漏。历史压缩包、日志、
散列索引及交叉引用需要逐组复核；不要全局替换后假定冻结证据仍然相同。

路径扫描器单元测试和证据索引校验器单元测试使用虚构路径及临时 Git 仓库。独立核对
了 E15 包索引 99/99、E17 证据索引 345/345 和 VirtIO-GPU 证据索引 305/305；这些
仅是基础提交现有文件的哈希一致性检查。原始串口日志恢复后，时钟/IRQ 索引 27/27、
Aurora SDK 复核索引 22/22 均匹配；恢复前分别有 8 项和 2 项不匹配。PR #41、#44 的脱敏导出与原始索引分别保留
来源和 SHA-256 映射，不能把导出描述为原始字节；详情见各 PR。

新检出并设置 `core.autocrlf=true` 的首次复验失败：只保护串口日志时，索引所覆盖的
其他 JSON/日志仍被转换。规则扩展至整个 `docs/reports/` 后，另建新检出，以上
10 份索引合计 1132/1132 文件匹配，10 份恢复日志也逐项匹配原摘要；失败的首次检出
作为本地诊断保留。此检查不证明未涵盖的索引、归档成员或客体行为。
