# exec 显式保留通用通道

W1 前台 exec 需要同 PID 保留终端通道；现有 sys60 会关闭所有通道，直接放开 libc
exec 会破坏会话。新增通用显式扩展：调用方以 sys60 bit32 选择带最多四个 token 的
扩展 entry，内核在变更前检查身份、去重和空槽，成功仅保留列明端点；默认仍全部关闭，
失败不更改旧通道。该机制不解释终端；协议静默、在途响应和 sequence 仍由用户态负责。
具体边界见通道契约。SDK `spawn_options` 允许替换镜像时传入保留列表。

通道定向探针增加重复 token 导致 exec 失败后旧连接仍可通信，以及成功 exec 后同 PID
端点通信；普通系统 build `3bb3fe49a96182db` 和探针交叉编译通过，ABI 文档一致性
通过。客体未运行，必须先提交再重建执行；终端 libc 的 descriptor/sequence 交接、
fork、权限与并发压力仍未实现或未验证。原 W1/W2 资格不由此完成。

提交 `e3b994c` 后客体首次运行失败：重复 token 的失败路径返回后继续执行，第二次
exec 已发生，但父进程在等待替换子进程消息时退出码 26；原探针让子进程发送后立即
退出，端点退出时可能先于父进程接收而关闭。串口 SHA-256
`6386313c40dbf2e786f2becd5828eae35a8cc661d006b7beb9f32a087c866d22`，回执在
`build/w1_exec_channel_run_e3b994c/`。这只是合理的竞态解释，尚非根因证明；探针
现增加父子确认握手，须提交后重测，不将该失败算作通过。

提交 `84b893d` 后同一 build `ef5e6ba933484146` 首次启动遇到
`BOOT_ERROR: iso_read`，未进入探针，串口 SHA-256
`b9c5fce69a7916920b2a098bdbd692c8589ca81b950a16283c002c34d45d0ff4`；对同一镜像
独立重试后通道限定组通过，包含重复 token 拒绝后旧连接可用，以及显式保留两端点
的成功 exec 后双向握手，串口 SHA-256
`895813563f8517a6259591d728e504b56c4dc855d690e642b805903043882fe8`。回执分别位于
`build/w1_exec_channel_run_84b893d/` 和 `build/w1_exec_channel_retry_84b893d/`。
这支持但不能单独证明首次消息丢失的竞态解释；ISO 初次失败原因未定位。终端 libc
尚未使用该机制，非参与者、待处理消息、资源压力及 fork 等仍未覆盖。
