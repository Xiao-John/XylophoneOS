# W1–W2 缺口核对与执行顺序

2026-11-02。依据 `docs/plans/ncursesw.md`，目标仍是单前台、真实串口终端的可复用
底座和独立 ncursesw 交付，而非仅让某个探针通过。此记录区分已获得的局部证据和
组合资格；每轮实现、探针和相关契约先提交，再以新源码重建匹配系统、SDK 和测试盘。

## 当前事实和主要缺口

- 终端服务和单线程 libc 已有受限模式、读写、select、显式启动及 exec 交接；
  现有客体证据分别见 0150–0159，不能组合成新系统的完整资格。带终端的 fork
  在 libc 明确返回 ENOTSUP；多线程 profile 亦不支持 fork/exec。
- 用户态服务目前只有一个应用通道对和一个接收线程。sys81 的创建者必须控制通道
  双方；父应用能控制待提交子进程，但不能控制作为兄弟进程的终端服务。通道按 PID
  认证，直接复制父句柄会被拒绝，共用应答槽还会混淆响应。原始 supervisor 创建的
  通道在创建者、任一端退出时关闭；不能忽略创建者生命周期而直接创建子代通道。
- 服务的四线程上限包括主线程、IRQ、控制接收和应用接收；为每个 fork 子进程新增
  等待线程不可扩展。sys81 多路等待最多四个句柄，已通过参数、超时及唤醒子集，
  关闭竞争、故障、并发和压力未通过。系统端点总数为 21，单通道创建者限额为 4，
  进程最多 8、fork 深度最多 3，容量和失败恢复必须以实际组合计算，不假设无限会话。
- Xsh 的 `result_line` 等待直接启动的应用退出后立即调用 `finish_application`；即使
  子代通道已独立，根应用先退出仍会使 shell 过早接回或关闭会话。设计还必须定义
  存活后代、前台撤销和 shell 恢复的边界，不能只修改 libc 和终端服务。现有前台取消
  登记只核对直接子进程，也不能直接证明整个后代树已停止。
- 组合 ncursesw SDK 曾在旧提交上完成四类局部客体检查（0152）；当前分支改变了
  系统和 SDK，必须重新构建、绑定并运行。宽字符、颜色、按键、重入与异常等每项
  必须按探针实际覆盖判断，旧证据不能转移。

## 执行方案及门槛

1. **冻结 fork 会话事务。** 先审计 fork prepare/commit/abort、通道身份与关闭、服务
   消息状态和资源上限。设计只允许已有授权的单线程终端客户端，为尚未运行的真实
   fork 子代申请独立双向通道；内核必须从现有权利和父子关系推导授权，不能信任
   用户自报 PID，也不能扩大到任意两个进程。确定谁持有通道及其退出对存活子代的
   影响；定义分配、服务登记、files 克隆、提交和失败回滚的顺序。子代在运行前必须
   完成服务登记，子代恢复 libc 客户端时验证自己的通道身份。父子请求不能共用应答槽。
   所有容量不足、登记失败、父进程或服务故障、子代退出与重复清理都要有界且可观察。
2. **实现有限会话与仲裁。** 服务用有界多路等待服务多个独立应用端点，并保持一个
   共享终端模式；规定输入读取互斥、并发请求的公平性、回复阻塞和关闭时的结果。
   等待集合变更、关闭与入队必须避免丢唤醒；应用恶意不收回复不能卡住控制面。不能
   凭现有 wait_many 子集推断这些竞态已经安全。按端点、进程及线程预算明确会话上限，
   超限失败时保留已有会话和资源基线。单线程 fork/exec 的行为单独覆盖，不扩大线程
   profile 或宣称完整作业控制。
3. **先提交再做 W1 客体门控。** 在正常 Xsh 上验证父子独立读写和模式共享、exec、
   退出/kill/服务故障、拒绝未授权与越权委派、关闭及竞态、超时、资源耗尽和回收；
   同时回归旧 console、pipe、dash 及系统设备/IRQ 路径。验证目标是真实行为而非
   单纯创建成功；不支持的重定向和异常顺序应有明确错误和证据。
4. **重建和验证 W2。** 使用同一提交的真实系统、普通 UTF-8 SDK、锁定 ncursesw
   源码和同源 terminfo 重做组合包及独立消费者；覆盖计划规定的宽字符分片/非法输入、
   CJK/组合字符、方向及功能键、局部刷新与颜色、尺寸/未知类型、重复进入/退出、
   故障恢复及资源预算。对当前探针未验证的要求补上可观察检查；不能模拟或声明不
   支持的功能明确列出，不以宿主构建替代客体执行。
5. **整合与交付。** 实施期间核对 main 和远端基线的新变化，解决冲突后重新做适用的
   组合门控；以最终提交绑定源码、系统、SDK、profile 与报告。保护其他工作区的未
   提交内容，将完成的变更整合到本地 main，再按用户授权发送 PR，并核对实际 PR 状态。

上面是执行顺序而非验收声明；具体 fork 授权和服务多路协议必须先完成详细设计和
资源核算，核对失败路径后再编码。任何新发现均先补充方案并验证，再进入下一步。
