# 终端子会话登记与接收方案

2026-11-02。现有服务主线程处理请求，IRQ、控制接收、应用接收分别占一线程，
已达每进程四线程限制。应用接收线程已经使用 `wait_many`，但只等待根应用一个端点；
现以会话记录保存该端点对及经内核认证的 peer，为后续有界会话表准备。现阶段仍不
接纳子进程，不能因预留记录声称已有多会话。

选定最多三个应用会话：根应用占一项，最多两个派生项。受控通道控制者总额为八，
控制通道两条加三个应用通道对恰为八；全局 21 端点和八进程池可能更早耗尽，故
必须允许资源不足并在失败时维持已有会话。该上限不是动态作业控制的承诺。

登记由现有应用在自身通道上请求，包含子端点对及子 PID；接收线程知道消息来自
哪一项，服务调用 `verify_fork_pair` 将新端点绑定到该来源的原端点，并在 building
状态、空槽和额度满足时加入会话表后应答。父进程收到成功应答并完成 files 克隆后
才提交 fork；失败时 abort，关闭派生端点。子进程从内核枚举的自身端点恢复客户端，
不得沿用父进程的 token 或请求序号。应答丢失时结果未知，父进程 abort 且不重试
同一事务；服务须从关闭事件撤除条目。

应用接收线程负责维护有界等待集合和消息来源，并在锁内发布单个待处理请求；主线程
按来源端点回复、共享设备模式。仅当接收线程能证明集合更新在重新等待前可见时才可
确认登记：特别注意 `next_request` 当前在主线程处理请求之前清除 mailbox，接收
线程可能先按旧集合重新睡眠。登记操作必须采用明确屏障或由接收线程原子处理，不能
仅添加数组。关闭与等待并发时要重查每个端点，将失效子项移出；根会话失效时按现有
进程树终止语义结束会话。各应用回复通道必须独立，不收回复的子项不能无限阻塞控制面
或使其他项的成功结果被误归属。逐项确定锁保护范围、等待唤醒、抢占顺序、阻塞读取
的中断结果和公平性，再开放服务操作。

拟分阶段实施：先保持单应用行为并整理会话记录；再实现有界接收与撤销并保持旧协议
回归；最后增加登记事务、libc fork 交接和权限/故障/资源探针。每阶段提交后使用
匹配系统与 SDK 运行客体检查，不能以宿主模拟或局部通过替代 W1/W2 完整验收。
