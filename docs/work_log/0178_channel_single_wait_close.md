# 单通道等待中的对端关闭

2026-11-02。现有客体探针覆盖 `wait_many` 中的对端关闭和句柄重验，尚未覆盖
单通道等待。内核检查通道当前状态并登记等待均在同一内核路径；对端关闭会唤醒等待者，
单通道等待返回 `sys_error_invalid_handle`（当前数值为 -1），随后重新查询已失效句柄
返回 `process_error_denied`（当前数值亦为 -1）。与之不同，多通道关闭唤醒返回 0，
需要消费者重验。首次实现误把多通道语义用于单通道，客体退出码为 68，未通过。

在既有双进程通道客体探针中保留第二个备用通道：接收端先发请求，发送端确认后延迟
关闭；接收端对该空通道执行有截止时间的单通道等待，必须得到无效句柄错误，重试也
必须得到句柄失效错误。两种错误值相同，因此该结果不能单独证明等待发生于关闭之前；
延时只是为该时序提供机会，不是确定性同步。维持后续 fork/exec 及清理检查。此项不
覆盖发送端因队列满而等待时的关闭，也不证明所有调度与故障组合。
提交后从对应源码重建系统与 SDK，在实际客体运行并记录证据。

由于关闭前与等待中关闭返回值相同，该结果不能证明等待者已登记；仍需设计可观察的
确定性同步验证，发送端阻塞关闭也未运行。

后续方案：单线程父进程收到确认后发送第二次握手，之后只调用备用接收通道的 wait；
子进程收到该握手后通过已有 `sys_tasklist` 观察父进程状态，只有看到 `W` 才关闭该
通道，观察有截止时间。握手排除父进程仍在前一次确认等待的可能；在此 fixture 路径
中父进程没有其他可能阻塞的调用。该观察只证明这个单线程、单核编排，不扩展为所有
线程或调度竞争。提交后需重新构建并运行客体，不沿用延时版本的通过结果。
