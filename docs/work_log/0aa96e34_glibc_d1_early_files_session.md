# 0aa96e34 · D1 启动文件会话交接

基于已验证的[原生文件映射组件](61e99048_glibc_d1_native_image_mapping.md)。本次实现将 G3
文件传输提取到 [xos_file_session.c](../../src/ports/glibc/sysdeps/xos/xos_file_session.c)。
TLS 安装前由单一启动方持有普通零初始化状态，并提供分离的请求和响应缓冲区。
传输直接调用已有的 XOS IPC；本机对象构建没有未定义符号，也没有 TLS 重定位。
已有 5 秒单次请求截止、响应校验、错误映射和传输失败闩锁继续使用同一实现。

健康会话交接核对当前 PID 和两个由内核认证的端点。旧阶段在交接后失去请求权，
晚期 G3 在既有会话锁内接手原请求编号、两个端点和失败状态。目标 G3 已初始化或
已持有会话时拒绝交接。已失败会话可以交接给同一进程，晚期继续报告失败，无需
查询已退出的服务。已有 startup v1/v2/v3 描述继续负责 FD 恢复。此处没有新增
系统调用、文件协议字段、传递句柄或解释器启动记录。

## 构建和原生客体验证

使用断网 Linux arm64 构建环境（GCC 16.2.0、GNU binutils 2.47），从验签的
GNU glibc 2.44 源码构建 C SDK，再生成含 `stdio_transfer` 的独立候选 profile。
从与公开提交 `057a19e2a42aebae453fe5bb8a0665e16afaffcf` 一致的构建输入
生成正常系统及已存在的专用文件服务退出测试系统。受测本地快照与公开快照之间
只有前序映射工作日志的文字差异。真实 dash ELF
来自已验收的独立 #231 工具包，SHA-256 为
`7dfabd45670c8164f62075b6f36633d7b91e9590748056c7cfdbc3e775fe57b9`。

[客体夹具](../../tests/glibc_d1_file_session_guest.py) 用链接器包装位置进入 TLS
安装前的阶段，随后进入真正的 XOS glibc 静态 CRT；其原生传输和后期 G3 都来自
实际 SDK 的 `libc.a`。QEMU 11.1.3 中，真实 dash 以 `<` 从 FAT 重定向子进程
stdin。夹具直接使用 v2 记录中的继承句柄，并对交接前后的同一打开实例验证：

- 早期连续读和偏移零的定位读均得到 `ABCD`，普通文件缺失返回 `ENOENT`，
  此时已处理 3 号请求。晚期公共 `read(0)` 继续得到 `EFGH`。接下来的 G3
  ping 收到 5 号回执。旧状态无法再次发送，第二次交接被拒绝。子进程和
  dash 都退出 0，客体前后均为 129696 空闲页、3 个任务和 1 个完成记录。
- 专用系统中同一夹具在第 4 个请求遇到实际 files 服务退出，早期收到
  `-EIO`。晚期公共 `read` 与原生交换均报告 `EIO`，后者的输出被清空。
  文件服务恰回收 247 页，其余任务完成后是 129943 空闲页、2 个任务和
  1 个完成记录。该场景只在显式测试镜像中执行。

宿主 ASan/UBSan 回归通过 G3 的 49 项会话和 FD 测试、15 组实际 files/FatFs
集成，以及 8 组扩展文件和 24 组终端测试。首次宿主复跑暴露 3 个 IPC 替身
缺少 PID 查询，补入各自的固定测试身份后通过。首次客体预检因系统较测试夹具
先建而发现源码清单不一致，两个系统均从提交后的源码重建后通过。当前 ABI 表的
值及号码唯一性检查通过。
