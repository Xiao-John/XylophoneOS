# XOS Revival 计划书：以 non-AI OS 开发为主线

2026-10-23 · v0.4 · 状态：计划修订，尚未进行本计划对应的实现与运行验证。

## 项目定位

XOS Revival 首先是一个供自己和朋友开发、练习、娱乐的独立操作系统项目。近期以 non-AI OS 开发为主：亲手建设一个微内核系统，逐步使其能够承载现有开源工具链，在系统内编辑、保存、编译和运行程序。

项目不以商业产品、论文发表、优于 Linux 或证明 AI-native 架构成立为成功前提。朋友对研究方向的支持不改变项目所有者当前更想进行 OSdev 的选择。独立 OS 是主要成果，不是论文的附件；研究与论文仅在以后确有兴趣和结果时另行开展。

“non-AI”表示当前不实现或安排系统级 AI 功能，不代表永久禁止用户态 AI 应用。现在只建设普通 OS 所需的机制，不为未来 AI 预留专用内核对象、强制能力契约或训练基础设施。同时，当前工程应主动保留转向系统级 AI 架构研究的空间：在建设普通 OS 功能时落实可替换接口、可信身份、生命周期、资源归属与可观测性，降低未来加入实验运行时和建立对照的成本。具体安排见“面向未来研究的架构预留”。这降低迁移成本，不承诺未来研究无需修改内核。

## 本轮修改与阅读方式

v0.4 新增：non-AI OSdev 仍为主线；面向未来系统级 AI 研究的通用边界随相应 OS 模块建设落实，不提前实现 AI 平台。以下同时保留 v0.3 已确定的路线调整。

- 确认 x86-64，替换旧版 AArch64 首选建议。
- 确认 OS 以 NASM + 受限 C++ 开发；具体语言子集仍作为工程建议待实施细化。
- 工具链主线改为 GCC/G++：宿主交叉编译、交叉构建原生 Seed、XOS 内开发、系统重建与工具链自举。TinyCC 从候选和必经步骤中移除。
- GCC 在本计划中只指 C/C++ 编译环境及必要配套，不要求 GCC 的全部语言前端。
- XCC 不重要、不必实现。GCC/G++ 可用后直接扩展移植；XCK 是开发工具套件的统称，不要求自研其中每个工具。
- AI Runtime、Router、能力网络、Linux 对照和 paper 均暂缓；旧设计保留在附录，不作为任务、ABI 或验收要求。

## 成功标准与版本边界

最终使用画面：朋友启动镜像，创建或修改源文件，在 XOS 内调用 GCC/G++ 及配套工具生成程序，由 XOS 装载执行；编译错误能够定位，程序崩溃能够恢复，正常保存关机后源码仍在。系统不需要模型、云账户或宿主代执行服务。

交叉编译是正常开发手段；独立运行不等于第一天即可原生编译。QEMU 提供虚拟硬件也不等于宿主代替 XOS 实现文件、进程或编译服务。

以下细分是建议里程碑，不把原生 GCC 的移植难度藏进一个很小的版本号。

| 阶段 | 主要交付 | 不应冒称的结果 |
|---|---|---|
| 0.0-boot | 独立启动、异常处理、基础内存管理、终端和调试 | 完整微内核、用户隔离或开发环境 |
| 0.0-user | 用户/内核隔离、任务、抢占、IPC、静态用户程序装载 | 原生编译或自举 |
| 0.0-dev | 最小文件与开发工具，可创建/修改内容并通过已实现的工具执行或装载新组件 | 只有宿主预编译程序时，不声称完成系统内源代码开发 |
| 0.1-port | 版本化 SDK/sysroot、运行库与兼容层、首批现有命令行工具移植 | 完整 POSIX 或完整原生 GCC/G++ |
| native-c/cpp | GCC/G++ 与所需工具在 XOS 运行，完成 C/C++ 多文件构建、执行与持久保存 | 编译器已经能重建自己 |
| system-rebuild | XOS 内从源码构建新版系统，导出/安装到测试镜像并启动验证 | GCC/LLVM 也已完成自举 |
| compiler-bootstrap | XOS 内重建选定 GCC/G++ 并进行自举比较和相关测试 | 所有语言前端与开源软件都兼容 |
| ecosystem | 逐个移植 CPython、编辑器、构建工具，后来再推进 Clang/LLVM | 必须先完成 XCC、AI 或论文 |

0.0-dev 的工具实现需要单独选定。早期“查看/编辑文件、装载宿主构建的程序”是有用的中间成果，但与“系统内把源文本转换成新可执行内容”分开记账。如果不采用任何较小现成工具，完整系统内源码开发就会更晚到来，不能用措辞假装提前完成。

## 实现边界：微内核与用户态

内核首先承担启动后的基本机制、地址空间与页映射、任务切换、定时抢占、受保护 IPC、中断交付、异常上报与资源回收。内核不理解 C++ 源码、文件路径、模型请求或应用业务。

用户态逐步承担启动/监督策略、程序装载策略、终端、文件与块设备服务、libc 适配和开发工具。初期用于 bring-up 的调试串口等临时内核实现应明确记录，不扩展成把所有服务放进内核的捷径。

初期只验证有限条件下的隔离与恢复，不宣称生产级安全。为终端和监督保留必要资源；无限循环、用户程序越界和内存耗尽都应有可观察的处理结果。驱动进入用户态不自动解决设备 DMA 隔离问题，相关能力按实际设备支持单独处理。

## x86-64 与 NASM + 受限 C++

平台已选定 x86-64，启动工具与具体硬件模型尚未选定。建议先使用成熟引导方案，减少非核心准备工作；是否自己写引导器可以由兴趣决定，不作为证明独立 OS 的必需条件。

建议复用 ELF64 与 System V AMD64 的常规函数调用约定。XOS syscall/IPC 接口另行设计，不因采用函数 ABI 而自动模拟 Linux。初期不支持 32 位兼容，不用开发机的本机 CPU 特性集合定义所有发行镜像。

NASM 用于启动、异常/中断入口、上下文切换等确有需要的架构边界；普通逻辑主要用 C++。必要的编译器内建函数与内联汇编可封装使用，不为了形式统一而全部改成外部汇编。NASM 处理手写汇编；GCC 生成的汇编使用其配套汇编器，不要求 NASM 直接替代 GNU assembler。

受限 C++ 建议如下，尚不是全部冻结的语言规范：

| 类别 | 初期建议 | 要解决的问题 |
|---|---|---|
| 类、enum class、constexpr、模板 | 允许适度使用 | 表达类型、尺寸与资源不变量，不制造复杂框架 |
| RAII | 用于正常控制流中的资源管理 | 异常关闭仍可使用作用域析构；不能替代崩溃后的系统回收 |
| 异常、RTTI | 内核初期禁用 | 减少早期运行时与故障路径复杂度 |
| 分配 | 显式分配器、明确失败语义和可调用上下文 | 不默认所有 new 都成功，不在禁止阻塞的路径随意分配 |
| 静态初始化、TLS | 全局动态构造、复杂局部静态初始化、thread_local 逐项受控 | 先具备对应初始化、同步与生命周期支持 |
| 标准库与虚函数 | 按具体依赖和用途审查 | 不把全部 STL 自动引入内核，也不无理由禁掉所有抽象 |
| C++ ABI/运行时 | 列出实际需要的辅助函数与符号 | freestanding 并不等于零运行库依赖 |

内核需审计 red zone、栈对齐、代码模型、编译器辅助调用和浮点/SIMD 使用。通常禁用内核 red zone；寄存器状态保存与生成代码约束必须一致。最终选项依据真实布局和反汇编/链接结果确认，不直接复制完整参数模板。

受限规则建议只覆盖自研内核与指定底层组件。用户态 GCC、LLVM 及应用可以使用它们所需的 C++ 功能和运行库，不能要求上游源码改写成内核子集。OS 使用受限 C++，与系统为应用提供较完整 C++ 环境，是两个层次。

## GCC/G++、Seed、XCK 与自举路线

XCC 是可选命名和定制方向，不设必须开发的任务。GCC/G++ 可用后即可继续移植，不能因尚无 XCC 而等待。XCK 作为 XOS 开发工具套件的统称，整合现成工具、目标配置、sysroot、运行库和构建说明；它的价值是可用与可复现，而不是组件必须原创。

设现有开发系统为 H：

| 产物 | build：构建地 | host：工具运行地 | target：生成代码的平台 |
|---|---|---|---|
| 面向 XOS 的交叉 GCC/G++ | H | H | XOS |
| 交叉构建的原生 Seed GCC/G++ | H | XOS | XOS |
| XOS 内重建的 GCC/G++ | XOS | XOS | XOS |

先用宿主工具链生成 freestanding 内核与早期用户程序；随后准备 XOS 的头文件、启动对象、库和工具运行环境；再交叉构建能在 XOS 内执行的 Seed。只有后者真正进入镜像并可编译新程序，才称原生工具链可用。

不用刻意选择古老 GCC 再逐版升级。优先选适配成本可控的稳定版本；Seed 与原生重建可以使用同一版本。升级新版是后续维护任务，自举验证不以版本升级为定义。确需中间版本时，应记录它减少了哪项依赖或解决了什么兼容问题。

### 分开处理的依赖

| 层 | 责任 | 首次验证 |
|---|---|---|
| 目标代码生成与驱动配置 | 复用 x86-64 后端，配置 XOS 目标、搜索路径和默认链接行为 | 不混用宿主头文件/库，产物目标正确 |
| crt 与编译器辅助库 | 入口、初始化/退出、libgcc 或对应辅助支持 | 无未解释符号，启动和返回路径真实 |
| libc | 分配、字符串、文件与其他实际接口 | 正常与错误路径符合所用语义 |
| C++ 标准库与 ABI 支持 | 原生工具及应用需要的 C++ 环境 | 选择的设施可用；缺少的功能明确列出 |
| 汇编器/链接器/归档工具 | 汇编、链接、静态库与目标文件检查 | C/C++ 多文件与静态库构建可运行 |
| 编译器运行依赖 | GCC 相关库及进程/文件/环境接口 | Seed 在 XOS 内完成真实编译任务 |
| 编译器构建依赖 | Shell、Make、文本工具、GMP/MPFR/MPC、生成器等按版本审计 | XOS 内完成实际配置和构建，而非仅运行现成二进制 |

GCC 可用是大门，不是所有软件自动可移植的保证。每次移植记录实际缺失接口与可复用改动，推动底座扩大。不要为了消除链接错误写“永远成功”的假接口。

libc 选择仍开放。newlib 可作为候选调查，但不能预设简单接入即可承载完整 GCC/G++。采用与 Linux 系统调用绑定较深的库，则需要相应兼容语义或维护移植。兼容层可置于用户态，不要求微内核模仿 Linux 内部设计。

### 原生 GCC/G++ 适配审计

1. 固定源码发布版本、依赖版本、构建配置及实际校验值，优先仅启用 C/C++ 与所需目标变体。
2. 分开列出编译器执行所需依赖和在 XOS 内重建编译器所需依赖。
3. 审计文件、目录、临时文件、内存、进程启动/等待、环境和错误语义；记录真实调用点。
4. 审计预定义宏、目标配置、启动对象、库搜索路径、链接器选项；不意外依赖 Linux loader。
5. 交叉构建时区分必须在 H 执行的生成工具与将在 XOS 执行的产物，不在 H 直接运行 XOS 程序。
6. 先运行小型 C 和 C++ 程序，再验证多文件、静态库、错误诊断和所承诺的库设施；保留相关上游测试。
7. 适配尽量集中于平台层；记录上游升级时必须维护的补丁，不把补丁规模当作成就。

### 后续依赖图不强行排成单链

能够在 XOS 内重建系统，不必等待 GCC 自举或 LLVM。若系统构建使用 NASM、脚本生成器或镜像工具，也需把相应依赖纳入 system-rebuild 验收，不能只编译内核对象文件就宣称整套系统重建完成。

CPython 可由 GCC 先行移植，并为后续构建工具提供支持；不要求等 Clang/LLVM 完成。Clang/LLVM 后续作为大型 C++ 软件和另一套工具链推进，按实际版本补齐 C++ 环境、构建工具、生成器及资源需求。它们是长期扩展目标，不是首个可玩 OS 的门槛。

## SDK 与程序装载的逻辑接口清单

这里确定职责与语义，不冻结 syscall 编号或 C 二进制 ABI。内核 IPC 之上可以有自己的 SDK，再由 libc 适配它。

| SDK 功能 | 必须明确的语义 | 首批用途 |
|---|---|---|
| 读/写/关闭句柄 | 短读短写、EOF、错误、无效句柄、资源归属 | stdin/stdout/stderr、源码和产物 |
| 打开/查询/定位文件 | 创建/截断标志、大小、偏移上界、只读权限、失败不假成功 | 编译器读取头文件和目标文件 |
| 目录与文件管理 | 列目录、创建目录、重命名、删除、文件名规则 | 编辑器、工程目录和临时文件 |
| 内存分配/释放 | 对齐、失败、上界、进程退出回收 | libc heap、编译器数据结构 |
| 启动/等待/退出 | argv、继承哪些句柄、退出码、崩溃状态 | shell 调用编译器与用户程序 |
| 时间 | 单调计时与可选墙钟分开 | 超时、工具日志、文件时间 |
| 错误映射 | 稳定错误语义，不把不支持伪装成成功 | libc errno/SDK errors |

不立即要求 fork、信号完整语义、pthread、网络 sockets、动态加载和 JIT。若所选编译器在选定模式下确实依赖它们，应记录实际调用点，决定适配、关闭功能或换候选。不能为了消除链接错误填一堆返回成功的空函数。

文件句柄是调用域持有的引用；传入整数不意味着获得任意全局文件。默认应用只能写工作目录和临时目录，sysroot 只读。早期权限简单可用即可，不要求先实现应用能力平台的全部授权语言。

## 静态 ELF 装载验收面

限定 ELF64、目标 ISA、端序和一种静态可执行类型。根据 program headers 装载受支持段，检查边界/整数溢出、filesz <= memsz、文件范围、地址范围、段重叠、页对齐和入口合法性；BSS 清零，建立栈、参数与初始句柄。

首轮拒绝 PT_INTERP、未支持的动态重定位与其他不支持特征，返回可读错误。权限由映射边界执行，避免可写且可执行页面；链接布局也必须配合。具体字段与目标 ABI 以所选 x86-64 ABI 文档为准，不能把本段检查表当成完整 ELF 规范。

编译器和其输出采用一致的调用约定、整数宽度、栈约定、返回和错误处理。x86-64 浮点/SIMD 状态不能被忽略：即使练习以整数为主，编译器、格式化或生成代码仍可能使用相应寄存器。应在配置审计中选择“明确限制且验证产物”或“实现必要上下文保存”，不能凭源码看起来没有浮点就假设安全。


## 源文件持久化与镜像

建议系统只读镜像与可写工作盘分开。早期工作盘可以是 QEMU 的块设备镜像；宿主文件承载虚拟磁盘不等于宿主代执行文件系统。运行中的 XOS 必须自己经块设备和用户态文件服务读写。

采用 FatFs 时，明确大小写、文件名、目录、时间戳和错误行为；其路径大小写语义不等于典型 Unix，打包头文件时检查名称冲突。正常关闭文件/同步并关机后重启能恢复，是首个持久化验收；突然掉电的一致性是另一个问题，不混为一谈。[S20]

只对专用测试磁盘写入，不触碰宿主真实分区。原型不需要安装器或修改朋友的机器启动盘。源码备份可以通过关机后导出工作盘或显式传输完成；不要求先移植 Git 或网络栈。

## 给朋友的第一版交付清单

- 可启动镜像、可写工作盘、带版本的 SDK/sysroot、符号文件。
- 一条清楚的启动方式和经过测试的宿主要求；不发布尚未跑通的命令作为“开箱即用”。
- 五页以内的使用说明：启动、文件、编辑、构建、运行、错误恢复。
- 三项练习规格：命令行整数统计（固定输入输出）；多文件字符串/词频小工具（验证头文件、链接与文件）；终端小游戏或数论练习（验证输入、循环与状态）。具体实现留给朋友。
- 故障演示：越界访问、无限循环、内存耗尽各有清楚的恢复方式；坏程序不应迫使重建系统镜像。
- 版本内接口清单和不支持功能；升级镜像前如何保存工作盘。

初次上手建议观察目标为 30 分钟内完成第一次编辑—编译—运行。它是待验证的可用性目标，不是目前已有结果。记录朋友在哪里卡住，以改善系统，而不是考核朋友。


## 面向未来研究的架构预留

目的：以后可以在 XOS 上加入可替换的智能运行时、应用能力组合与资源调度实验，并把“共同运行时的收益”与“OS 机制的额外收益”分开验证。当前只落实通用 OS 也需要、且在模块首次实现时成本较低的边界。下表是工程建议；用户确认的是保留研究空间，并非已经接受某种 capability 系统、IDL、异步 IPC 或共享内存架构。

### 随主线落实的边界

| 预留点 | 当前应做什么 | 将来支持什么 | 当前不必实现 |
|---|---|---|---|
| 机制与策略分离 | 内核只执行权限和资源机制；服务选择、重启、分配策略集中在可替换用户态模块 | 比较规则、学习型策略及不同服务部署 | 智能调度、模型路由或插件框架 |
| 服务接口独立于传输 | 为实际服务定义请求、返回、错误和所有权；把本机 IPC 编码封装在适配层 | 在 XOS IPC 和 Linux 用户态适配器上复用核心工作流 | 通用 RPC、全平台后端或统一 IDL |
| 可信身份与句柄 | 服务身份来自可信通信上下文；资源句柄有明确持有者、权限和失效条件；重用不得把旧引用变成新权限 | 显式授权、受限委托与撤销实验 | 完整能力代数、策略语言和跨机器身份体系 |
| 请求与服务生命周期 | 区分正常返回、业务失败、服务退出、传输失败和等待超时；服务重启不能悄悄延续旧连接身份 | 故障恢复、取消、结果未知与重规划实验 | 通用事务、所有操作的幂等性或恰好一次保证 |
| 数据所有权 | 当前采用有界复制；明确消息、缓冲区及文件句柄的生命周期，接口不传裸跨进程指针 | 后续增加只读共享对象或共享内存传输并做对照 | 零拷贝框架、分布式对象存储 |
| 资源归属与控制入口 | 记录任务/服务拥有的内存、队列和可用 CPU 统计；限制集中在可定位的模块，先实现必要上界 | 服务级配额与调度实验，之后再细化到请求 | 精确端到端工作流记账、云端费用调度 |
| 可观测性 | 使用单调时间；关键事件含任务/服务标识、事件类型与结果；用户态可附请求关联标识 | 延迟分解、故障因果追踪与不同实现比较 | 永久采集平台、自动上传或模型内容日志 |
| 可替换实现与可复现配置 | 通过普通构建/启动配置选择真实服务或测试替身；记录工具、镜像与配置版本 | 固定执行器/模型服务切换、故障注入与回放 | 热插拔、完整实验管理平台或稳定第三方插件 ABI |

“预留”不是预先分配 syscall 编号、填空结构体字段或设置大量未使用回调。优先让实际模块有明确接口和依赖方向；第二种实现出现时再提炼公共抽象。错误含义、所有权和身份来源尽早写清，二进制布局与编号允许版本内共同重建，不承诺永久 ABI 兼容。

有副作用的服务尤其要避免把“调用方等不到回复”定义成“操作肯定没发生”。当前可以明确报告结果未知；以后由具体服务加入操作标识、查询、去重或补偿。取消也应区分停止等待、提出取消请求和确认未执行，不能自动承诺撤销已完成的操作。

资源统计初期按任务/服务即可。共享服务代请求方工作时，不能将服务 CPU 统计直接宣称为精确请求成本；细粒度归属留待真实需求。请求关联标识仅用于追踪，不作为授权凭据。日志默认不收集任意消息载荷、源码或未来模型上下文；控制日志体积，并保留关闭追踪的构建/运行方式，测量时记录追踪是否启用。

### 未来转入研究的路径

当项目所有者决定启动研究时，从一个具体的跨应用工作流或资源调度问题开始，复用上述边界：

1. 先实现确定性执行器与几个真实服务，明确授权、副作用和故障场景。业务逻辑尽量通过窄平台适配层调用系统服务。
2. 增加 Linux 用户态适配器，复用可复用的契约、数据与执行逻辑；不要求整个 XOS 内核或 POSIX 层跨平台。不同后端不能保证的语义明确报告。
3. 模型服务作为普通用户态进程接入，可以替换为规则或录制输出。Mock 只验证系统行为，真实模型质量与成本另行测量。
4. 比较应用自行集成、共同用户态运行时、XOS 特定机制三层贡献。权限保证、任务负载和硬件条件不同则不能直接归因于 OS。
5. 有证据表明某项内核机制是瓶颈或限制时，再增加可开关的实验实现；保留可启动的基线配置与已有 OS 验收。

研究不必等待完整 GCC 自举或 LLVM 移植，也不因当前保留接口就自动启动。实际选题、文献审查、Linux 基线与论文任务在研究启动时确定。附录仅为候选资料，不能反过来冻结当前内核。

## 后续取舍规则

- 新工作优先回答：是否帮助系统启动、调试、运行程序、保存源码、承载工具，或让自己和朋友更愿意使用？纯兴趣功能也可做，但明确它占用的主线时间。
- 可复用的兼容接口比一次性软件特判更值得积累；不为追求抽象而先造通用平台。
- GCC/G++ 适配困难时，定位具体运行环境缺口；不自动恢复 TinyCC 路线或转成自研 XCC。若要改变已确认路线，届时再明确讨论。
- 研究失败、Linux 更快或没有 paper，均不是停止 OSdev 的条件。
- AI 支线目前不排期、不采购算力、不设论文里程碑、不作为版本验收。通用接口、身份、生命周期和可观测性预留随 OS 主线落实；以后重启研究时另写研究问题与实验计划，不自动激活附录全部设想。
- 本轮不修改或创建 OS 源码仓库；进入实现后遵守该仓库的实际约定。版本号、精确库选择和启动参数以真实构建为准，不捏造已跑通的命令。

# 最小原型与实验契约 0.1

状态：可选的应用协作实验，非 OS 主线前置条件。P 类建议；定义实验语义，不是稳定公开标准或已实现 API。

## 场景与边界

系统为虚构用户 fixture-user 查询 2026-11-03 的一段行程。所有站点、车次和日历内容均为合成数据。只考虑单程直达列车；不建模票额、票价、换乘、跨境、夏令时、路线地图和真实交通波动。

给定出发站 ST-A、到达站 ST-B；允许出发时间为 00:00Z（当地 08:00）；必须在 02:00Z（当地 10:00）前抵达会场。车站至会场的固定转移时间为 1800 秒，额外裕量为 900 秒。时间计算统一用 UTC，Asia/Shanghai 仅用于显示。

日历查询窗口为 00:00Z, 04:00Z)，忙碌窗口为 [02:00Z, 03:00Z)。在本实验的封闭领域规则中，busy 只用于证明出发到到达会场之间的时间可用；任务明确指定 02:00Z 为到达期限。不要从任意日历中的“第一件事”自动推导用户意图。

可行性条件：train.departure >= earliest_departure；train.arrival + transfer_seconds + buffer_seconds <= arrive_by；从 earliest_departure 到“arrival + transfer + buffer”的半开区间不得与 busy 区间相交。等于 arrive_by 可以通过。提供者必须明确声明日历覆盖整个请求窗口；不完整覆盖不得当作空闲。

按 arrival、departure、trip_id 的升序选择第一个可行车次。没有可行车次返回业务结果 NO_FEASIBLE_TRIP，不写草案。默认数据可行车次为 TR-A、TR-C，选中 TR-A。

## 三个业务能力、四个方法

| 方法 | 输入 | 输出 | 副作用与约束 |
|---|---|---|---|
| timetable.query.v1 | 两站、出发窗口 | 有来源标识和版本的车次快照 | 只读；响应完整性明确；本轮无分页 |
| calendar.busy.v1 | calendar_id、时间窗 | 不含标题/参与者的忙闲快照 | 只读；必须验证资源与时间范围授权 |
| draft.create.v1 | workflow_id、operation_id、被选车次、完整行程和两个快照引用 | draft_id、store_epoch、已提交记录 | 真实写入；授权、幂等与提交必须在存储边界执行 |
| draft.status.v1 | workflow_id、operation_id、store_epoch | committed/rejected/not_found，或 epoch_changed | 只读；查询本身也检查主体和工作流作用域 |

方法定义见 [method-catalog.json。JSON Schema 只校验结构；关系比较、授权、去重、覆盖完整性、过期和原子提交不能用“schema 已通过”代替。

## 逻辑请求与传输

请求包括 protocol、request_id、workflow_id、method、wait_budget_ms、payload。request_id 标识一次传输尝试；operation_id 只用于写入的逻辑操作，多次重试保持不变。写入 payload 内的 workflow_id 必须等于外层 workflow_id。

不在请求体内接受可自我声明的权威 caller_id、角色、授权令牌或内核 capability。Linux 从受控通道/可信代理绑定主体；微内核后端从受保护端点身份绑定主体。fixture 中的主体名字仅是测试配置。

协议采用 method 的主版本。未知方法或版本在执行前拒绝。一个接口内未知字段默认拒绝，演进通过显式版本处理；本实验不承诺灵活的旧客户端向前兼容。

JSON 是宿主测试和文档表示，不要求微内核实现完整 JSON-RPC。可以使用有界类型化消息，由边缘适配器保持同一逻辑对象。内核 syscall ABI 不等于业务契约。

实验默认上限：单消息 64 KiB；一次时刻表最多 64 项、busy 最多 32 项；引用最长 128 字符；队列每端点最多 16 项；超限显式返回 RESOURCE_EXHAUSTED/INVALID_ARGUMENT，不能静默截断为“完整”结果。数值时间为整数秒；UTC 文本限制为整秒 Z 格式。后续编码若不同必须重新测量解析与复制开销。

## 快照与对象

每个快照有 provider_id、snapshot_id、source_version、observed_at、valid_until、coverage 与 complete。快照是不可变的。snapshot_id 是身份引用，不是授权凭证，也不是全球唯一真实性保证。

每次创建草案时验证引用属于当前工作流已接收的快照，且内容中 trip_id、站点和时间一致。创建前再次检查有效期、授权和可行性。快照过期返回 STALE_SNAPSHOT，重新查询与重新评估；不能无声换入新数据后声称旧选择已获确认。

本轮可信提供者保证快照业务内容；不证明时刻表真实。含恶意描述、额外文本或伪造类型的数据，执行器不得当作指令。未来接入远端时需要重新定义来源可信性。

## 写入与幂等：避免虚假的“恰好一次”

第一轮只保证在同一存储进程实例、同一 store_epoch 内的进程级故障恢复。草案代理可以崩溃，存储进程不在该故障集合内。

幂等键是 (可信主体, workflow_id, operation_id)。存储服务在一个串行化提交点完成：授权/作用域检查、epoch 检查、已存在键检查、业务验证、写入草案和去重结果。草案和去重结果不能分两次独立提交。

同键同语义 payload 返回既有结果；同键不同 payload 返回 OPERATION_CONFLICT。比较使用规范化后的完整业务字段，时间统一 UTC、整数无歧义；request_id、等待预算不参与业务相等判断。不依赖不稳定的普通 JSON 字节顺序，也不省略任何会影响副作用的字段。

对于已提交项，重试可以在重新验证“有权查询该项”后返回历史结果；不应因快照后来过期而把已提交操作改写为失败。新提交仍必须验证当前授权与快照有效性。

| 观察 | 执行器能得出的结论 | 后续动作 |
|---|---|---|
| committed | 在该 epoch 已提交 | 记录 draft_id；不再创建新逻辑操作 |
| rejected 且明确未提交 | 此操作被确定拒绝 | 返回原因；修改业务内容必须使用新 operation_id |
| 连接断开/等待超时 | 结果未知 | 标记 UNKNOWN，查询同键同 epoch |
| status=not_found | 查询时没有记录 | 不能证明没有在途请求；同 epoch 下可用同键重试，由提交端去重 |
| store_epoch 改变 | 旧去重与结果知识可能丢失 | 禁止自动重试写入，报告需要核对；不声称断电恢复 |

多个相同请求并发到达也必须只创建一个草案。有限的重试次数是运行策略，不是幂等的替代品。

为使内存边界真实可测，实验存储每个主体/工作流最多保留 64 个已记录操作。达到上限时，在产生副作用前返回 RESOURCE_EXHAUSTED；同键结果查询与重试不额外占用一条。一个 epoch 内不静默淘汰去重记录。需要清空时必须改变 epoch 并使旧操作进入核对状态，不能一边释放去重信息一边继续承诺旧请求可安全重试。

## 超时、取消、撤销

wait_budget_ms 是单次等待预算，不是跨机器绝对时间，也不承诺副作用在预算到达时自动撤回。执行器可停止继续下发新步骤；已提交操作不会被“取消”撤销。本轮不提供通用 cancel RPC。

写入授权在实际提交点检查。若撤销已在线性化顺序中生效，新写入拒绝；若写入在撤销前已提交，则保留事实。不得声称可以召回已经读走的数据或远端已经执行的动作。

## 工作流状态

准备输入 → 获取完整快照 → 确定性筛选 → 验证候选 → 提交草案 → 完成。

任一只读步骤明确失败则不进入写入。写入无答复进入 UNKNOWN；只允许查询或符合上表的同键重试。流程日志必须保留 UNKNOWN，不能为了显示整洁把它显示成失败。

## 最小开发闭环与 AI 插入点

终端能输入一个新的过滤脚本，在独立的预留脚本保护域中运行，返回候选 trip_id。替换脚本不要求重新构建整个系统镜像。脚本只获得快照中授权且需要的字段；最终约束仍由可信执行器检查。

AI 实验也只返回候选 trip_id 和供展示的说明。说明不作为授权或正确性依据。固定算法、脚本、录制输出、真实模型均通过同一个候选入口；它们没有 draft.create 的访问权。

该原型验证的是一个受限协作问题。它不声称已经验证任意自然语言任务规划、任意工具链编排或 AI 的通用协作能力。

# 授权、隔离与生命周期

状态：可选应用协作实验设计。OS 主线的基本进程隔离仍必需，但不要求先实现本文件的全部业务授权。所有保证都必须由后续实现和故障试验提供证据。本文件不声称已建立安全证明。

## 信任边界

| 组件 | 初期信任与持有权力 | 不能交给它的权力 |
|---|---|---|
| 内核与启动配置 | 地址空间、端点/通道身份、调度与资源分配机制 | 理解自然语言意图、判断车次业务真实性 |
| 启动/监督服务 | 创建或初始化实验域、分配已声明资源、回收指定域 | 因模型要求而无约束扩大权限 |
| 可信执行器 | 工作流状态、业务约束检查、使用预授予的范围权限 | 任意用户资源、全局所有写入凭据 |
| 日历提供者 | 验证 calendar_id、窗口和权限；返回最小忙闲数据 | 把可读权限扩展为任意外发权限 |
| 时刻表提供者 | 提供本实验可信的固定数据 | 把描述字段变成执行指令 |
| 草案代理 | 转发被验证的命令和查询；允许故障注入 | 独占幂等状态、可绕过存储服务直接写入 |
| 草案存储 | 提交点授权、去重、结果与内容的原子修改 | 无版本地重置 epoch 后继续承认旧幂等保证 |
| 脚本/模型候选器 | 接受获准快照摘要，返回候选标识 | 草案写入、全日历读取、默认网络访问 |
| 宿主测试驱动 | 注入合成输入、记录外部观察 | 替 XOS 完成运行时必需的调度、存储或脚本执行 |

三个业务能力不等于只能有三个进程。为隔离故障，草案代理和存储应处于不同故障域。第一轮故障集合排除内核、监督器、执行器和存储本身崩溃；后续扩大集合时必须更新保证，不能把窄测试写成全系统恢复结论。

## 最小授权配置

- executor-fixture 可以调用指定 timetable.query.v1；读取 calendar-fixture 的 [2026-11-03T00:00:00Z, 2026-11-03T04:00:00Z)；仅在 WF-001 命名空间创建和查询草案。
- planner-fixture 只接受 executor 经策略筛选的候选输入；没有 calendar、draft 或网络端点。
- timetable-a 与 timetable-b 是显式允许的提供者身份。替换时允许改变部署清单中的绑定，但不修改消费者算法。
- 没有任何来自模型的字段能够增加授权。opaque_ref、snapshot_id、operation_id 和 manifest 均不是安全 capability。
- 权限检查在真正服务和存储边界执行。前端执行器的检查属于纵深验证，不能成为唯一防线。
- 动态注册或服务发现暂不开放；只有部署配置能绑定接口版本与提供者身份。能力描述只说明功能，不能授予访问权。

Linux 参考映射：独立进程与受控本地通道；通过进程/通道凭据或可信代理绑定主体。实现时先配置无不必要凭据的子进程、文件/网络访问限制和 cgroup 配额，再评价保证。仅使用随机端口、请求体 caller 字段或靠程序自觉不越权不合格。

微内核参考映射：分开的保护域、明确的端点权利和内存区域；业务范围由可信提供者检查。若使用自写内核，必须先验证隔离和不可伪造通道身份，不能把“handle 是整数”当成实现了 capability。

## 数据生命周期

本轮复制有界不可变快照。提供者拥有原始数据，调用方拥有返回副本；工作流结束或显式失败后释放副本。日志只记录 ID、状态、计数、时长与拒绝原因，不记录日历标题、完整 prompt 或凭据。

缓存先关闭。未来缓存键至少区分主体、授权作用域/版本、数据源版本、查询、接口版本和有效期；读取缓存也重新检查当前权限。撤销权限不保证擦除过去已经合法复制的数据。

若以后引入共享内存，需要另行设计映射者、读写权利、页生命周期、配额归属、版本更新、进程退出与撤销后的行为。微内核能力保护内存对象不自动解决业务对象的生命周期。远端调用继续使用传输对象，不能要求跨机器共享虚拟地址。

云端升级默认禁用。未来允许升级时，应在数据离开本机的出口执行策略检查；让模型自己承诺“不会泄露”不构成控制。两项合法读取组合后可能产生更敏感的信息，最小原型只检验已声明范围，不宣称实现通用信息流控制。

## 资源与故障遏制

实验默认值：每个候选器内存预算 16 MiB；请求体不超过 64 KiB；队列 16 条；一次候选执行等待 500 ms；普通 RPC 等待 1000 ms。数值用于首轮可重复试验，并非生产承诺；实现前可因基线合法工作集不足而调整一次并记录，不能看完对照结果后单边改变。

CPU 不能只依赖脚本主动 yield。需要宿主调度/内核抢占与监督路径。Lua allocator 限额作为解释器内部保护，地址空间/物理内存分配仍需系统边界约束。共享服务收到的工作应归属到请求主体，并限制在途量，避免通过代理逃避自己的配额。

必须预留终端控制与监督服务的可运行资源。耗尽测试至少包含无限循环、反复分配、消息洪泛和代理不回复。结果记录 p95 控制响应和最长失联，不仅检查“最后没有死机”。

本轮不连接 DMA 设备或 GPU，不根据用户态服务隔离推断未来设备驱动已经安全。后续设备支持需要单独考察设备内存访问与故障边界。

## 重启、撤销和错误报告

草案代理重启后从存活的存储查询结果，不从自己丢失的内存猜测。存储重启生成新 epoch；旧操作进入核对状态。脚本域退出后回收其私有内存、端点引用和队列项；不可把旧句柄无版本地重新绑定成别人的资源。

错误码保持小而明确：INVALID_ARGUMENT、UNSUPPORTED_VERSION、PERMISSION_DENIED、RESOURCE_EXHAUSTED、UNAVAILABLE、STALE_SNAPSHOT、OPERATION_CONFLICT、EPOCH_CHANGED、INTERNAL。传输等待超时单独标记 outcome=unknown；它不能被草案 create 的业务 error 冒充为“明确未写入”。

审计记录包含 request_id、workflow_id、operation_id（如有）、可信主体、方法、提供者/epoch、阶段、结果、耗时与策略版本。它用于解释行为；本轮不宣称抗篡改、持久或具有完整隐私证明。

# 验收、对照与证据

## 三组证据分别报告

2. **平台证据**：授权、数据语义、替换提供者、失败处理、接入成本。

## 用例执行协议

输入为 fixtures/scenario.json，错误变体为 fixtures/negative-cases.json，完整执行条目为 experiments/acceptance-cases.json。每条记录后端、构建哈希、环境、种子、前置状态、注入点、观察事件、状态及证据位置。未实现用例保持 not_run；不以 skip 填充通过率。

固定数据时钟为 2026-11-02T23:00:00Z。业务时间来自合成时钟，不能因现实日期越过夹具 valid_until 导致测试失效。RPC 等待与性能测量使用实际单调时钟；两者不能混用。

对故障用例设置可观察注入点：before_dispatch、before_commit、after_commit_before_reply、after_reply。不要仅用随机 kill 的时间猜测是否发生了提交。随机压力作为补充，不能代替确定性边界测试。

## 第一阶段通过条件

- 对指定错误输入，副作用计数必须为零；越权或伪造身份只要出现一次成功，就不能通过。
- 基线只创建一个 TR-A 草案。相同幂等键重复/并发提交仍只有一个草案；改变 payload 被拒绝。
- after_commit_before_reply 触发 UNKNOWN，查询后回到 committed，草案数量仍为一。
- 存储 epoch 改变后，不自动重试旧写入；这是正确保护行为，不算恢复失败。
- 替换时刻表提供者只修改部署绑定/提供者清单和相应 provider_id；业务算法不变。
- 候选器缺失、崩溃或返回非法候选，不阻止终端、固定工作流及系统内开发继续工作。
- 地址空间越界访问不能读写另一个域的私有页；违规域故障后其他域可继续工作。

这些是有限故障模型下的验收，不是完整安全证明或形式验证。

## 可用性与开销测量

建议首轮固定资源压力持续 60 秒，重复 10 次；记录终端探测 p50/p95/max、丢失响应数、工作流成功数、内存峰值与队列峰值。初始实验阈值：终端探测 p95 不超过 250 ms、最长无响应不超过 1 s。它只是初始可用性目标；若宿主过慢，应在比较之前共同重定标并保留原设置，不能宣称硬实时。

正常工作流的测量：单并发与 8 并发，冷启动另记；热启动先做 50 次预热，再做每组 1000 次、5 组。失败和超时保留在分母中，不能只统计成功样本。数据变大时使用 1/16/64 项与相同语义，超出上限以拒绝结果评估，不临时扩大某一后端。

记录总耗时及分段：发现/绑定、授权、序列化、IPC、业务、存储、等待；使用跨域可比较的单调时钟或外部观察，注明精度。不能把每段 p95 相加当成总 p95。模拟器内部虚拟时间与宿主墙钟分开报告。

初期不设“XOS 必须快 20%”一类无依据目标。优化是否保留，以端到端收益、变异范围和新增复杂度共同判断。

## Linux 对照

Linux 对照与 Revival 使用同一逻辑契约、同样的提供者边界和状态模型。Linux 必须使用进程隔离、真实身份绑定、可用的资源控制和访问限制；不能拿未经隔离的单进程 demo 作安全参照。[S14][S15]

性能比较分两层：第一层比较业务平台在同一宿主上的额外开销；第二层在可匹配硬件/虚拟化条件下比较两个 OS。若加速方式、驱动、编译优化或安全保证无法匹配，只报告描述性结果，不归因于微内核本身。

| 比较项 | 必须保持相同 | 允许不同但必须记录 |
|---|---|---|
| 正确性 | 数据、规则、权限、故障点、预期结果 | 消息编码、底层 IPC |
| 隔离 | 威胁对象、可用权限、故障集合 | 内核机制、配置方式、可信组件规模 |
| 开销 | 工作量、资源限额、并发、冷/热状态 | 具体实现及其原因 |
| 工程投入 | 能力范围、验收用例 | 实现时间、代码/配置量、调试困难 |

## 接入成本实验

使用两条路径：应用直接写集成；使用公共契约/SDK。两者都必须完成相同的授权、幂等和故障要求，否则不能比较。

第一轮由同一人顺序实现可找出问题，但学习效应很强，只算探索。正式比较请独立开发者实现第二提供者，只提供公开契约、夹具和验收要求；记录提问次数、发现的未定义语义、适配文件、修改消费者的次数、实际工作时间。条件允许时交换实现顺序。

平台固定投入单独记账。成本比较采用 C平台(N)=平台初始成本+各次接入成本+维护成本；C直接(N)=各次直接集成成本+维护成本。没有观测值前不计算虚假的回本应用数量。若每次接入仍需新增双方专属约定，H01 受到削弱。

## 决策规则

- 若任何核心权限/幂等用例失败，先修复或缩小保证，不增加模型功能。
- 若 Linux 同样实现保证且更省维护，记录事实；OS 依然按用户明确的爱好与原生开发目标继续。比较帮助选择机制，不决定项目存废。
- 若静态域不能满足脚本替换/恢复，记录具体缺口，再决定使用 seL4 API 或改变工具实现；不立即扩成动态桌面 OS。
- 若 Lua 移植依赖过大，比较其他现成工具；不得为了避免改选而继续堆完整 POSIX。
- 若没有独立接入证据，只能说“完成原型”，不能说“已验证生态”。

# Router 与生态价值：何时值得继续

本阶段只准备实验，不训练模型、不采购算力、不接入用户账户，也不宣称已有采用者。

## 首个 AI 接口

输入是政策允许的候选车次、明确到达期限和必要忙闲摘要；输出是候选 trip_id。模型输出进入与脚本相同的验证器。模型说明仅供展示，不能作为授权、事实或执行依据。

模型服务的外部合同包括版本标识、输入上限、预算、已知数据出口、响应状态及取消的真实语义。模型超时按 UNAVAILABLE 处理候选器，但不能把它传播成内核或基础工具失效。高敏感输入默认不出本机；首轮真实模型实验也使用合成数据。

## Router 是否有必要

首先使用三种可比较执行路径：确定性程序、本地小模型、外部较强模型。若具体模型尚不可用，则先保存执行路径接口，不能用 Mock 成绩推断模型质量。

硬性策略先过滤合法集合：可外发数据、允许提供者、任务能力、可用内存和硬预算。Router 仅在合法集合中选择；它不能通过较高置信度绕过权限。

| 对照组 | 作用 |
|---|---|
| fixed-deterministic | 已知规则任务的下界基线；不能处理的任务明确失败 |
| fixed-local | 观察本地路径独立完成率与真实资源成本 |
| fixed-strong | 质量和成本参考；不假设一定最优 |
| rules | 按类型、隐私、常驻状态、长度、队列选择 |
| encoder-classifier | 学习预测各路径成功/代价，使用相同可见特征 |
| generative-router | 复杂理解是否足以抵消额外推理成本 |
| oracle-offline | 根据各路径实测结果估计可改善空间；不可部署，也不能泄露给在线策略 |

RouteLLM 已有偏好数据路由的研究，因此“有一个分类 Router”不是自动成立的差异化。XOS 若贡献新结果，应来自具体系统条件、执行反馈或更可靠的约束整合，而不是换一个模型名称。[S18]

## 数据与标签

先做不超过 200 个任务的探索集，用于找问题，不做统计显著性宣告。任务覆盖：明确规则可解、含糊但可澄清、不可行、提供者不可用、数据过期、隐私限制、上下文变长、候选器错误。

只有存在值得学习的差异后才构造训练集。按意图家族、模板和数据快照分组切分，建议 60/20/20；近似改写不能跨训练/测试泄漏。另设时间后移/模型版本变化的压力集。真实用户数据不默认收集。

训练标签来自候选路径的实际执行成功、约束违反、延迟、资源和费用。强模型可协助解释/标注，但其偏好与分析不是最优路径的事实标签；也不要求访问私有内部推理过程。高代价错误优先人工或确定性复核。

记录路由特征时区分决策时可知的输入与事后结果。不得把答案质量、实际输出长度等未来信息作为在线输入。

## 端到端评价

总耗时包含路由、排队、模型加载、推理、工具执行和失败后的升级；总费用包含失败尝试，不把本地路径成本写成零。电力、驻留内存和模型加载成本可先单独记录，不强行转成不可靠货币值。

环境组合：冷/热模型、空闲/拥塞、正常网络/高延迟/断网、不同内存预算。每次记录硬件、量化格式、模型版本、上下文长度、可用路径和是否命中缓存。缓存默认关闭；开启时严格区分模型上下文缓存、业务数据缓存与结果缓存。

比较顺序：先排除违反硬性策略的方案；再在相近任务质量下比较成本/延迟的 Pareto 前沿。汇总时报告每类任务和最严重错误，不能只用平均成功率掩盖误写入。

若规则已经接近离线 oracle，暂缓训练；若主要损失来自模型冷启动，则优先研究驻留与排队策略；若主要损失来自模糊接口，则先修契约。Encoder-only、生成式决策或扩散模型都没有预设优先权。

## 能力契约如何形成长期收益

复用成熟表达：MCP 已有工具发现与 schema，WIT/Component Model 已有组件接口与资源表达。本轮使用窄 JSON 逻辑对象便于实验；之后评估适配，不另造覆盖所有应用的 IDL。两者都不能替代项目自己的副作用和信任语义。[S16][S17]

为了避免封闭中心，公开契约、错误定义、夹具与兼容测试；允许独立实现注册表、执行器和提供者；不要求唯一账户、唯一云服务或签名注册中心；应用能在 Linux 等宿主运行。任何认证或发现服务获得的权力也必须列入可信边界。

同一个提供者可能同时有 GUI、HTTP/MCP 适配和本机接口。适配器必须明确哪些保证可以保留：例如远端缺少幂等键/结果查询时，映射为“结果可能未知”，不能假装与本地存储具有同样恢复保证。

版本兼容靠明确的语义和独立实现验证。字段叫 arrival_time 但时区不同，类型同为 string 仍不兼容。公开示例应覆盖空结果、边界时间、不完整数据、重试和撤销，不仅成功路径。

最早的生态证据是：第三方仅依靠材料就能接入，替换/升级的成本下降。真正的采用动机、维护负担和付费意愿仍需访谈/试用；没有发生的访谈不能写成结论。
